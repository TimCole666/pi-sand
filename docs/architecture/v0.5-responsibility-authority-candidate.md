# v0.5 responsibility authority candidate

- **Status:** candidate, not architecture authority
- **Date:** 2026-09-02
- **Purpose:** capture the converged design before one final runnable proof
- **Do not use this document to modify v0.4 or merge PR #64.**

This document is a decision snapshot for the next prototype and later `/to-spec` synthesis. It is intentionally narrower than the current v0.4 architecture and the draft v0.5 PR.

## Product promise

> **The user gives responsibility, not workflow.**

> **One Chat Box != One Agent != One Runtime. It is one responsibility interface.**

v0.5 proves one concrete product journey:

```text
Telegram 1:1
  -> one coding Goal
  -> user may correct the Goal while work is in flight
  -> stale execution cannot newly publish to GitHub
  -> stale execution cannot authoritatively declare completion
  -> user can leave and return
```

The product entry surface is Telegram private 1:1 chat on a phone. OpenClaw native Chat, Discord, Slack, group chat, multiple simultaneous Goals, and multiple Telegram conversations are not v0.5 requirements.

v0.5 assumes one Goal at a time. It does not define queueing, scheduling, replacement UX for a second independent Goal, or parallel Goals.

## Ownership

### pi-sand owns

Only the semantics OpenClaw and Codex do not currently provide:

```text
Obligation
  id
  current_revision
  status

InputDecision
  input_id
  obligation_id
  classification
  resulting_revision?
```

`revision` is a scalar responsibility epoch, not a separate aggregate. A durable `InputDecision` records the transition that produced a new revision.

pi-sand does not store a second transcript. The exact Telegram/user text remains host-owned and is referenced by `input_id`.

### OpenClaw owns

```text
Telegram durable custody
accepted_generation
admitted_generation
required authority owner
canonical Codex thread/turn binding
turn lifecycle
protected GitHub capability
GitHub publication request/reconciliation
one-shot mutation authorization
one-shot authoritative final dispatch
Telegram delivery
```

### Codex owns

```text
coding execution
thread context
turn execution
native tools/runtime mechanics
normal tests/build commands
```

## Revision and authority generation are different axes

`revision` answers:

> Did the accepted responsibility change?

It belongs to pi-sand.

`accepted_generation / admitted_generation` answer:

> Has a newer durably accepted user input entered this protected conversation that has not finished responsibility admission yet?

They belong to OpenClaw.

Derived state:

```text
input_pending := accepted_generation != admitted_generation
```

Do not persist a separate `authority_pending` boolean.

A status question may advance the host generation without changing the pi-sand revision.

## Hard responsibility boundary

The guarantee begins when OpenClaw durably accepts the Telegram message, not when the user taps Send on the phone.

For a protected conversation, durable acceptance must atomically establish both:

```text
channel ingress accepted
accepted_generation := accepted_generation + 1
```

Once that commit wins, new protected GitHub mutation and authoritative final delivery are closed until the input is admitted.

A normal plugin callback after durable enqueue is too late. The v0.5 host contract requires a bounded OpenClaw upstream facility at the durable ingress transaction.

## Required Session Authority Owner

A protected conversation persists an explicit required dependency such as:

```text
required_authority_owner = "pi-sand"
required_authority_contract = "v0.5-pinned"
```

It is deliberately not a generic policy framework.

The required owner participates at exactly three hard boundaries:

1. protected durable input admission;
2. actual consequential GitHub mutation;
3. actual authoritative final dispatch.

If the owner is missing, incompatible, unavailable, times out, or cannot read its durable state, protected behavior fails closed. Ordinary OpenClaw extension hooks remain ordinary hooks.

## Correction semantics

A correction commits user control before changing execution:

```text
Telegram correction durably accepted
  -> accepted_generation advances
  -> effect/final gates close
  -> InputDecision committed
  -> current_revision N -> N+1
  -> old turn permanently loses protected authority
  -> establish execution that can represent revision N+1
  -> admitted_generation catches up
  -> effect/final gates may reopen
```

### Same-turn `turn/steer` is not an authority boundary

Current Codex cannot prove that a dynamic tool call from an active turn was generated after a particular `turn/steer` input. `DynamicToolCallParams` contains `threadId`, `turnId`, `callId`, tool and arguments, but not the originating `clientUserMessageId`.

Codex issue #36994 explicitly states that `turnId` is insufficient because multiple `turn/steer` inputs can be accepted in one active turn:

- https://github.com/openai/codex/issues/36994

Therefore `turn/steer` may still help behavior, but it must never re-grant protected revision authority in v0.5.

## Fresh-turn candidate rule

Until Codex supplies trustworthy per-input descendant provenance, a material correction that needs protected authority uses a fresh native turn on the same Codex thread.

Candidate protocol:

```text
1. correction is durably accepted; generation is pending
2. revision N+1 is durable
3. retire T1 permanently from protected authority
4. interrupt/end T1
5. observe the canonical terminal lifecycle for T1
6. reject every later T1 tool/final event forever
7. ensure old workspace writers are stopped or isolated
8. start a fresh native turn on the same thread
9. observe the canonical native T2 lifecycle identity
10. bind T2 -> current revision N+1
11. admit the pending generation
12. only T2 may request protected effect/final authority
```

Do not bind authority from a provisional `turn/start` response ID. Codex issue #36866 documents a case where a second `turn/start` can return a submission ID that never becomes the lifecycle turn ID:

- https://github.com/openai/codex/issues/36866

`turn/interrupt` also cannot be treated as a proof that every old computation has ceased. Codex issue #36926 documents interrupted-turn lifecycle defects, and old/background processes may require separate cleanup:

- https://github.com/openai/codex/issues/36926

The remaining prototype must prove whether the pinned OpenClaw/Codex combination can satisfy this fresh-turn authority fence without adding a new pi-sand runtime/supervisor subsystem.

## Physical GitHub fencing

v0.5 protects one consequential external effect family: GitHub publication.

The only write path is:

```text
Codex
  -> OpenClaw protected github_publish path
  -> host authority linearization
  -> Gateway-owned credential-bearing publisher
  -> GitHub
```

The Codex execution placement must not independently possess GitHub write capability. In the protected deployment, Codex must not be able to reach a usable GitHub token, authenticated `gh` profile, Git credential helper, SSH private key/agent, OS keyring credential, write-capable GitHub MCP/App, or equivalent bypass.

Process separation alone is not capability separation. Use a sandbox/dedicated execution identity/placement that withholds the credential from Codex. The Gateway remains the credential owner.

## Publication linearization

Creating a durable publication request is not sufficient authorization for every later remote mutation.

Each consequential remote mutation step must re-enter the shared host authority ordering immediately before transmit. For example, a push and a later PR create are separate mutation steps.

Conceptually:

```text
claim one-shot mutation authority for
  generation G
  canonical turn T
  current revision R
  logical effect K
  mutation step S

then transmit
```

If a correction's durable acceptance commits first, the claim fails. If the mutation claim commits first, the mutation may be transmitted and a later correction cannot revoke bytes already sent.

OpenClaw already has strong GitHub publication mechanics: durable requests, repeated authority checks, exact workspace/commit identity, remote branch readback, PR markers/lookups, and restart reconciliation. pi-sand must not duplicate those mechanics.

## `effect_key`

Keep `effect_key` as a minimal semantic identity, not an Effect framework.

A logical key may be derived from:

```text
(obligation_id, revision, effect_kind, candidate_fingerprint)
```

It answers only:

> Is this recovery attempt continuing the same logical external operation?

OpenClaw owns the durable publication request and remote reconciliation.

## Completion

Codex saying `done` is only a completion candidate.

The semantic gate is intentionally thin. It checks responsibility facts such as:

```text
candidate belongs to the current revision/current canonical turn
no unadmitted user input exists
required protected effects are resolved
explicit Goal-required blocking facts are satisfied
```

If the user explicitly required CI to pass, existing GitHub/OpenClaw/Codex facilities provide the fact. pi-sand does not build a generic Reviewer, Evidence framework, Completion DSL, or verification engine.

Semantic authorization is still not final delivery. OpenClaw must take a one-shot authoritative final-dispatch claim at the actual outbound delivery boundary. A correction that wins the shared ordering first blocks the final dispatch.

## Restart

A protected conversation remains protected across restart.

```text
required authority owner missing/incompatible
  -> protected mode unavailable
```

Never silently downgrade to ordinary fail-open hooks or ordinary Codex behavior.

Old executor state may remain useful as telemetry/work product, but it does not regain effect/final authority unless the host can prove the exact current canonical execution binding and generation state.

## Remaining proof gate

Architecture research is considered converged except for one runnable question:

> **Can the pinned OpenClaw/Codex combination establish `retire T1 -> canonical T2` such that all late T1 tool/final events are permanently rejected, and such that old workspace writers cannot continue mutating the authoritative workspace when T2 receives protected authority?**

This is a prototype question, not an implementation task.

Pass if existing host/runtime mechanics plus only the already-accepted bounded OpenClaw authority facility can establish the fence.

Revise if one additional small host/runtime seam is required.

Falsify the candidate if satisfying the invariant requires pi-sand to own Codex orchestration/runtime mechanics, a new supervisor/runtime, or an equally large subsystem.
