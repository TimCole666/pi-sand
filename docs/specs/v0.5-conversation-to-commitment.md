# v0.5 Spec: Conversation to Commitment

- **Status:** Proposed release spec
- **Date:** 2026-09-02
- **Architecture:** ADR-0001 + ADR-0002
- **Current-release boundary:** v0.4 remains governed by Issue #48 plus current source/tests/PR #62. v0.5 must consume the v0.4 responsibility kernel rather than reopen it.

## 1. Release thesis

v0.5 proves that ordinary conversation can safely create and change durable responsibility while autonomous execution is already in flight.

> **User messages should change the work, not interrupt the work.**

The release is successful when a user can hand over a coding outcome, leave, send later corrections/requirements/approvals from the same chat, survive crashes/restarts, and receive a verified Result without the runtime depending on one AgentSession retaining the latest instruction in context.

The core path is:

```text
user input
    -> durable/correlatable ingress
    -> interpretation proposal
    -> admission/control authority
    -> Commitment + skeletal Completion Contract
    -> current execution
    -> Evidence
    -> immutable Result snapshot
    -> ResultDelivery
```

Every hard authority boundary must reject stale execution ownership, stale approvals, stale candidates, stale proof, and earlier unresolved responsibility-affecting user input.

## 2. Product journey

The primary acceptance journey is intentionally one coding Commitment.

```text
User:
“修好 issue #27，测试过告诉我”

-> Commitment accepted
-> skeletal Completion Contract
-> coding execution begins

User while work is running:
“不要修改数据库 schema”

-> durable control mutation
-> affected admitted work explicitly revalidated/invalidated
-> incompatible stale output cannot commit
-> best-effort live Pi steer is optional

User:
“reconnect 也测一下”

-> same externally visible outcome
-> Completion Contract proof requirement elaborates
-> compatible work survives

crash / restart

-> current control/contract survive
-> exact execution ownership reconciles
-> stale AttemptRun cannot regain mutation/effect authority

runtime reaches an exact merge candidate abc123
-> HumanGate(candidate=abc123)

User:
“可以”

-> approval applies only if abc123 is still the exact live subject

candidate is replaced by def456
-> approval for abc123 cannot authorize def456

accepted current Evidence satisfies current Contract
-> Result seals against one immutable proof snapshot

first Result delivery fails/ambiguous
-> same Result remains sealed
-> fresh delivery generation retries
-> no implementation Attempt is restarted
```

The release must also prove explicit cancellation/non-success closure without inventing a successful Result.

## 3. Scope

v0.5 owns only the minimum semantics required by the journey above.

Required release capabilities:

1. distinguish conversation-only input from a new/changed durable responsibility;
2. accept one eligible coding Commitment from ordinary language;
3. preserve user-grounded outcome, explicit constraints, and current authority;
4. admit a skeletal Completion Contract and elaborate proof without silent scope expansion;
5. apply responsibility-affecting user corrections durably before relying on live Pi steering;
6. fence irreversible/authority-consuming transitions behind earlier unresolved ingress;
7. explicitly retain/revalidate or invalidate affected admitted work after control changes;
8. bind execution mutations to current Attempt/AttemptRun ownership;
9. bind HumanGate answers, RemoteEffects, and Evidence to exact current candidates;
10. allow stale execution to record provenance-bearing information without granting authority;
11. seal immutable Results against exact current proof snapshots;
12. separate Result from ResultDelivery and retry delivery without re-execution;
13. terminate cancelled/impossible responsibility explicitly without synthesizing success;
14. recover all of the above across process/runtime restart.

## 4. Explicit non-goals

v0.5 does **not** implement the long-term architecture in full.

Do not require:

- generic Dynamic Work Ledger or rich dependency graph;
- external tracker integration;
- multi-worker scheduling;
- generic TaskRequirement or JoinSpec language;
- generic ResourceLease abstraction;
- generic AgentMessage subsystem;
- permanent PlannerAgent, ClarifierAgent, ReviewerAgent, or orchestration persona;
- learned/complex model router;
- durable CurrentIntentFrame database;
- ConversationGraph or duplicated transcript store;
- universal generation/compatibility object;
- mandatory ControlImpactReceipt chains;
- browser/Environment/Computer support;
- automatic inferred social follow-up commitments;
- sophisticated multi-Commitment pronoun targeting.

The first implementation may support zero or one active Commitment plus one exact HumanGate. Ambiguity outside that bounded product journey may safely ask the user rather than introducing a general semantic router.

## 5. Reuse boundary

Reuse Pi for ordinary live execution mechanics:

- AgentSession and live message history;
- model/tool loop;
- context-window management and compaction;
- steer/follow-up queues;
- Skills representation/discovery/loading;
- ordinary tools and model selection;
- Extension interception/UI mechanics where an execution strategy chooses to use them.

v0.5 must not build a second session/context/Skill/tool-loop framework.

Conversation storage belongs primarily to the Pi/channel substrate. pi-sand requires durable/correlatable ingress ordering and source provenance for authoritative transitions; it does not require copying every casual chat message into a second domain database.

## 6. Admission and conversation interpretation

Conversation cognition is proposal-only.

Conceptually:

```text
User message
    -> deterministic exact targeting if available
    -> semantic interpretation if necessary
    -> proposal
    -> admission/control transaction
```

A minimal interpretation may identify:

```text
target:
  conversation-only
  new responsibility
  current Commitment
  exact HumanGate

kind:
  status/side question
  new Commitment
  control/constraint change
  proof/contract refinement
  cancel
  Gate answer
```

Exact enum/API is not locked.

### Admission boundary

Use three conceptual stages:

```text
Conversation-only
Provisional discovery
Accepted Commitment
```

For the primary coding journey, ordinary explicit delegation such as:

```text
“修好 issue #27，测试过告诉我”
```

may move directly to Accepted Commitment when the runtime can safely identify:

- the subject/outcome it now owes;
- explicit known constraints/exclusions;
- the current authority ceiling/policy;
- the return route;
- bounded policy/budget sufficient to proceed;
- a safe route for progressively discovering proof without redefining the outcome.

Unknown root cause, exact implementation route, files, or exact tests do not by themselves require a question.

Model confidence is evidence for interpretation, not authority to create responsibility.

### Assistant future promises

The runtime must not say it will autonomously return later unless a real durable responsibility/background mechanism has been admitted.

No phantom:

```text
“I’ll check and come back later”
```

without durable work/recovery/return ownership.

## 7. Intent/Control vs Completion Contract

The accepted Commitment preserves user-grounded responsibility:

```text
what outcome is owed
explicit constraints
explicit exclusions
current delegated authority
source/correction provenance
```

The Completion Contract expresses how the same responsibility will be proved.

```text
Intent / Control
= what we owe and may do

Completion Contract
= what Evidence must establish for closure
```

A skeletal Contract is valid at admission.

### Contract refinement rule

Strengthening proof of the already-owed externally observable outcome is Contract refinement.

Examples:

- reconnect regression test;
- restart verification;
- CI evidence;
- exact-candidate verification;
- additional deterministic checks needed to avoid falsely claiming the original outcome works.

Adding something materially new is not refinement. New externally observable behavior, deliverable, material scope, or newly authorized side effect is an Intent/Control change.

Practical test:

```text
If removing the requirement could let us falsely claim
that the already-promised outcome works,
it is probably proof refinement.

If adding it makes the user receive, experience, authorize,
or become responsible for something materially new,
it is control/scope change.
```

No separate `IntentAnchor` table is required.

## 8. Durable control before steer

A responsibility-affecting user correction commits to durable runtime truth before live execution steering is relied on.

Example:

```text
User:
“不要修改数据库 schema”

-> interpret current Commitment target
-> accept durable control change
-> determine affected admitted work
-> explicit retain/revalidate/invalidate decisions
-> optional best-effort steer current Pi AgentSession/AttemptRun
```

If the current AgentSession dies before seeing the steer, restart/successor execution still reconstructs the current durable constraint.

A status question or unrelated side question must not bump control or invalidate work.

## 9. Affected-work revalidation

A responsibility-affecting control change does not imply every current piece of admitted work is invalid. It also does not allow compatibility to be inferred by inertia.

Affected work must receive an explicit outcome:

```text
retain / revalidate
invalidate
supersede
```

Exact names are implementation-specific.

Safe reversible local computation may continue while revalidation is pending, but unresolved/stale output may not:

- complete current work;
- satisfy a blocker;
- become accepted Evidence;
- authorize/transmit a RemoteEffect;
- resolve a HumanGate;
- seal a Result.

Do not introduce a ControlImpactReceipt subsystem just to record this decision. Ordinary control/WorkRef transitions are sufficient unless implementation evidence proves otherwise.

## 10. Ingress authority-release barrier

A durably received but not yet responsibility-classified user input closes dangerous authority-release boundaries.

It does **not** globally suspend execution.

```text
input durably accepted
        -> classification pending

reversible local work
        -> may continue

RemoteEffect transmission
Result sealing
        -> fenced
```

If the input is classified as conversation-only/unrelated, the barrier reopens without changing responsibility.

If it changes responsibility, affected authority remains closed until the control mutation and required work/effect/proof revalidation are complete.

The implementation may use an ingress watermark/barrier or an equivalent ordering mechanism. Do not use this requirement as a reason to create a second conversation state machine.

## 11. Attempt / AttemptRun ownership and recovery

v0.5 reuses v0.4 Attempt semantics and must preserve this established distinction:

```text
Attempt != AttemptRun/process
```

### Crash before launch

If Attempt A2 is already authoritatively committed and the process crashes before launch:

```text
restart -> launch SAME A2 exactly once
```

Do not allocate A3 merely because A2 had not launched yet.

### Reclaimed running owner

If a genuinely running AttemptRun is proven dead/reclaimed and a replacement becomes current, a delayed/resurrected old process must not regain authoritative mutation rights merely because it reconnects or emits output.

A minimal implementation may use transactional claim/ownership identity, generation/token, heartbeat/process observation, and reconciliation or equivalent mechanisms.

Do not generalize this into ResourceLease unless later releases prove a broader need.

## 12. Stale producer information vs decision authority

A stale/superseded AttemptRun may append useful provenance-bearing information:

```text
log
diagnostic
Artifact
Observation
candidate evidence claim
```

The record must be attributable to the producing Attempt/AttemptRun and relevant stale basis.

Its existence does not grant current authority.

The stale producer may not directly cause:

- current WorkRef completion;
- dependency satisfaction;
- Evidence acceptance;
- Gate resolution;
- RemoteEffect authorization/transmission;
- current control mutation;
- Result sealing.

Current cognition/verifier may inspect stale information and separately propose/accept current Evidence when appropriate.

## 13. HumanGate exact-subject semantics

HumanGate answers bind to an exact currently applicable subject.

Example:

```text
G1: approve merge of abc123
User: “可以”
```

The answer applies only while G1 and candidate `abc123` remain current/applicable.

If the candidate becomes `def456`, the old approval is historical and cannot transfer.

Late answers to retired/stale Gates must not resurrect authority.

The exact storage may use Gate revision, candidate digest, one-shot approval identity, or another minimal representation. v0.5 locks the semantic, not a universal Gate schema.

## 14. RemoteEffect authority

The primary coding RemoteEffect used by acceptance tests may be an exact publish/merge action.

Conceptually:

```text
prepared effect
    -> exact candidate
    -> current authority/HumanGate as required
    -> ingress barrier
    -> transmission
    -> receipt/readback/reconciliation
    -> Evidence where applicable
```

If a user correction arrives while an external effect is already in flight:

- record new control immediately;
- attempt cancellation only if the provider supports it;
- treat outcome as uncertain until exact readback/reconciliation;
- never assume cancellation succeeded;
- never blindly retry an ambiguous effect.

## 15. Evidence

Worker self-report, tracker state, Artifact creation, test output, or a Skill saying “done” is not automatically accepted Evidence.

Accepted Evidence must be bound to the current candidate and applicable proof basis before it satisfies the Completion Contract or an admitted blocker.

Evidence admission/acceptance is runtime authority, not worker authority.

## 16. Result sealing

A canonical Result is sealed only when the current Completion Contract is satisfied by current applicable accepted Evidence and no earlier unresolved ingress is allowed to change that responsibility/proof basis.

The Result sealing basis is immutable by identity.

Conceptually:

```text
Result R1
  control_basis       = C7
  contract_revision   = K4
  accepted_evidence   = {E12,E15,E19}
  candidate           = abc123
  work_lineage        = W8/A3/AR5
  ingress_basis       = I42
```

Exact physical representation may be version IDs, digests, immutable refs, or equivalent.

Reading R1 later must reconstruct the same accepted proposition.

> **A sealed Result is immutable.**

Later control changes, new contract revisions, Evidence changes, candidates, or delivery failures may not rewrite R1.

Input arriving after Result sealing must be interpreted as current/follow-on responsibility. It may affect an undelivered return obligation or create/supersede future responsibility, but cannot silently reopen/rewrite the historical Result.

## 17. ResultDelivery

Result existence and Result delivery are separate facts.

```text
Result sealed
    -> Delivery generation 1
         -> delivered
         -> failed/blocked/uncertain
              -> Delivery generation 2
```

A delivery retry:

- reuses the same canonical Result;
- does not create a new implementation Attempt;
- does not regenerate the Result;
- uses a fresh fenced delivery generation/attempt identity;
- preserves ambiguity honestly when transport acknowledgement cannot prove delivery/non-delivery.

For ordinary interactive v0.5 work, successful Commitment discharge requires both:

```text
outcome satisfied by sealed Result
AND
admitted return/delivery obligation reaches an accepted terminal state
```

A transient delivery failure leaves the successful Result intact and only the delivery obligation open.

## 18. Explicit non-success Commitment closure

Commitment terminality must distinguish successful outcome satisfaction from non-success closure.

Required v0.5 examples:

- explicit user cancellation;
- acknowledged impossibility under the current admitted authority/constraints.

These close responsibility explicitly without fabricating:

- successful Result;
- accepted success Evidence;
- Contract satisfaction.

Exact terminal enum is not locked. Do not introduce vague automatic `abandoned` behavior as garbage collection.

If a Result already exists but its admitted return obligation becomes permanently impossible, the Result remains historically true; broader Commitment closure follows explicit delivery/return policy and must not falsify/delete the Result.

## 19. Failure-injection acceptance matrix

The release must pass all ten trace families below. A test must prove the dangerous interleaving, not merely the final happy database row.

### V05-FI-01 — Ingress vs RemoteEffect transmission

Setup: current exact merge candidate `abc123` is ready to transmit.

Inject:

```text
User: “不要 merge”
```

Durably accept the input, pause responsibility classification, then allow the old merge path to attempt transmission.

Required:

- reversible local computation may continue;
- provider transmission does not occur while classification is unresolved;
- once classified as responsibility-affecting, current control becomes durable;
- old effect authority cannot be reused after restart.

Forbidden: the merge transmits before the earlier durable input is classified/reconciled.

### V05-FI-02 — Ingress vs Result sealing

Setup: current K3 + accepted Evidence appears closure-ready.

Durably ingest:

```text
“reconnect 也测一下”
```

Pause classification and allow seal path to race.

Required: no Result seals against K3 while the earlier input remains unresolved. Once classified as proof refinement, K4 must be satisfied before sealing.

Positive control: an unrelated status/side question, once classified conversation-only, reopens the barrier without mutating the Commitment.

### V05-FI-03 — Crash/restart AttemptRun ownership

Case A: Attempt A2 was committed but process crashed before launch. Restart launches the same A2 exactly once.

Case B: a truly running owner AR4 is proven dead/reclaimed; AR5 becomes current. If AR4 later resumes:

```text
information append with AR4 provenance -> allowed
current-authority mutation             -> rejected
RemoteEffect release                   -> rejected
```

### V05-FI-04 — Stale Artifact without Evidence authority

A stale AR4 produces Artifact D1 after its basis is stale.

Required:

```text
D1 persists with AR4 provenance
WorkRef remains unfulfilled
accepted Evidence set remains unchanged
```

until a current-authority verifier/cognition path separately accepts applicable Evidence.

### V05-FI-05 — Explicit work revalidation after control mutation

Current work B planned a schema migration; current work C is independent.

User says:

```text
“不要修改数据库 schema”
```

Required:

- control mutation is durable first;
- B receives explicit invalidate/revalidate/retain outcome and old validity cannot commit;
- C remains valid when unaffected;
- continued process activity is not interpreted as compatibility.

### V05-FI-06 — Immutable Result snapshot

Seal R1 against exact control/contract/Evidence/candidate/ingress basis.

Then change live control, contract, Evidence, candidate, WorkRef state, or delivery state.

Required: reading R1 reconstructs the same original proposition. R1 identity, Evidence membership, candidate, and sealing basis remain unchanged.

### V05-FI-07 — Delivery retry without re-execution

R1 is sealed. Delivery generation 1 fails/timeouts/returns ambiguous acknowledgement.

Required:

- Result count unchanged;
- R1 unchanged;
- implementation Attempt count unchanged;
- fresh delivery generation exists;
- canonical delivery payload still references R1.

### V05-FI-08 — Explicit non-success closure

Case A: user cancels C1 while running.

Case B: runtime reaches an accepted conclusion that the outcome is impossible under admitted constraints/authority.

Required: explicit terminal non-success closure; no fake successful Result or Evidence.

### V05-FI-09 — Exact candidate fencing

Human approves Gate G1 for candidate `abc123`.

Before effect/closure, candidate becomes `def456`.

Required:

- approval for `abc123` cannot authorize `def456`;
- Evidence for `abc123` cannot satisfy an exact-candidate requirement for `def456`;
- prepared effect for `abc123` cannot silently retarget to `def456`.

### V05-FI-10 — Recovery trusts ownership truth, not Task projection

Construct/replay a crash window where coarse Task projection and exact execution ownership disagree.

Required:

- exact ownership facts win;
- reconciliation deterministically recovers/reclaims the appropriate execution identity;
- projections converge afterward;
- no duplicate authoritative owner;
- repeated reconciliation is idempotent;
- no model judgment is required for ownership recovery.

## 20. Cross-trace assertions

Where relevant, all acceptance traces must also prove:

### Idempotency

Replaying the same user input, wake, terminal event, Gate answer, or delivery retry request does not duplicate an authoritative transition.

### Causation

For every accepted responsibility-affecting mutation, runtime evidence can answer:

```text
What source input caused this?
What prior basis was replaced?
What exact current subject did it affect?
```

### No stale resurrection

Once explicitly retired, an old process, approval, candidate, WorkRef basis, or delivery generation cannot become current again merely because its delayed message arrives.

### No model-owned authority

No hard acceptance result may rely only on “the model probably followed the latest instruction.” Runtime-enforced truth must be observable.

## 21. Required implementation seams

The release needs only enough implementation/storage to expose these semantics:

```text
durable/correlatable inbound input ordering
Commitment control mutation
skeletal Completion Contract revision
affected-work applicability/validity
exact Attempt/AttemptRun ownership
current-vs-stale mutation enforcement
HumanGate exact candidate applicability
RemoteEffect pre-transmission authority check
Artifact producer provenance
Evidence acceptance
immutable Result sealing basis
ResultDelivery generation
explicit Commitment terminal disposition
```

This is a correctness surface, not a prescribed table list.

Several concepts may be represented by existing v0.4 rows/events plus small version/provenance additions.

## 22. Implementation constraints

- Prefer existing v0.4 storage/transaction seams over schema redesign.
- Do not migrate v0.4 architecture for reuse purity.
- Do not start v0.7 rich work/dependency semantics early.
- Do not duplicate Pi conversation/session/context/Skill mechanics.
- For hard fences, validate authority at the last responsible transition boundary, not only in prompts.
- Failure-injection tests should stop at deterministic seams so dangerous interleavings are reproducible.
- Where a test concerns crash recovery, cross a real process/runtime restart boundary or equivalent authoritative persistence boundary.
- Where a test concerns an external effect, prove provider transmission did not occur, not merely that local status later changed.
- Where a test concerns a stale actor, make the stale actor actually attempt the forbidden mutation and assert rejection.

## 23. Release exit criteria

v0.5 is complete only when all ten failure/race families pass and the primary user journey works end to end.

At that point the runtime has demonstrated:

```text
conversation can safely amend durable responsibility
without depending on the current AgentSession surviving;

user control can race with autonomous execution
without losing authority ordering;

crash/restart cannot resurrect stale execution authority;

stale information remains usable without becoming authoritative;

completion cannot outrun already-received user control;

external effects cannot escape through an ingress-classification race;

current accepted Evidence seals one immutable historical Result;

delivery failure cannot cause completed implementation to execute again;

cancellation/impossibility can terminate responsibility honestly.
```

## 24. Handoff to v0.6 and v0.7

After v0.5, responsibility/control semantics are reused rather than redesigned.

### v0.6

Apply the proven kernel to the first non-coding execution environment:

```text
Environment + Browser + Download + Artifact
```

The release should prove concrete Environment/browser/profile ownership and Artifact/effect semantics without re-solving Conversation -> Commitment.

### v0.7

Add the Minimal Dynamic WorkRef Ledger with `max_parallel = 1`:

```text
A accepted
-> B runnable

B discovers prerequisite C
-> proposal
-> admit C
-> B explicitly blocked

C accepted
-> B runnable

B accepted
-> current Commitment proof satisfied
-> Result
```

Ingress fencing, AttemptRun ownership, HumanGate candidate fencing, Evidence acceptance, Result sealing, and ResultDelivery are inherited from v0.5.

## Final release statement

> **v0.5 is complete when ordinary conversation can race with autonomous execution, crash recovery, external effects, verification, and delivery without allowing stale or unresolved authority to escape across a hard runtime boundary.**
