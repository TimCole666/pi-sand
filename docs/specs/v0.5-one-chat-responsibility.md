# v0.5 Spec: One-Chat Responsibility

- **Status:** Proposed
- **Date:** 2026-09-02
- **Architecture:** ADR-0001 + ADR-0002
- **Evidence gate:** responsibility-zero prototype + issue #65 fresh-turn authority prototype + focused architecture review #71

## 1. Release thesis

v0.5 proves one product promise:

> **A user can hand one coding outcome to one Telegram chat, correct it while work is in flight, leave and return, and trust that stale execution cannot silently publish or declare success for the current request.**

The user does not choose agents, runtimes, workflows, task graphs, or models.

Example:

```text
User: 帮我把 #123 修好，CI 过了以后告诉我。

User later: 不要改数据库 schema。

User later: reconnect 也测一下。

User later: 可以，发出去吧。

System: ✓ 已完成
```

## 2. Fixed v0.5 product scope

```text
one Telegram private 1:1 conversation
one active Goal / Obligation
OpenClaw as the responsibility-correctness host/testbed
official Codex app-server as coding executor
one protected consequential-effect family: GitHub publication
one pinned verified OpenClaw + Codex + process-containment capability contract
```

Not in scope:

```text
second independent Goal behavior
parallel Goals
scheduler / DAG / worker pool
multi-agent product topology
Discord / Slack / groups / multiple Telegram chats
browser/computer product implementation
memory / Skills runtime
arbitrary SaaS effects
host portability
Hermes/Grok Bot integration
generic reviewer/evidence/effect frameworks
generic process-containment runtime
```

## 3. Responsibility state owned by pi-sand

### Obligation

```text
id
current_revision
status
```

v0.5 may have zero or one active Obligation.

### InputDecision

```text
input_id
obligation_id
classification
resulting_revision?
```

Classification values:

```text
initial_goal
correction
ordinary_question_or_status
```

The classification for the same durable `input_id` is idempotent across retry/restart.

`revision` is an integer/scalar responsibility epoch. There is no separate Revision aggregate/table requirement.

### Semantics

```text
initial goal
  -> create Obligation at revision 1

correction
  -> advance current_revision

ordinary question/status
  -> current_revision unchanged
```

The host owns the exact message text/transcript. pi-sand references durable input identity rather than copying the conversation.

## 4. Host authority state

OpenClaw owns the operational authority facts:

```text
required_authority_owner
required_authority_contract
accepted_generation
admitted_generation
canonical Codex thread identity
canonical current Codex turn identity
retired turn identities
protected execution/containment profile identity
protected writer inventory/quiescence state
publication request/reconciliation state
final dispatch state
```

Derived:

```text
input_pending := accepted_generation != admitted_generation
```

A protected effect/final cannot be authorized while `input_pending` is true.

## 5. Durable Telegram ingress

The product guarantee begins when OpenClaw durably accepts the Telegram update.

The following must share one host-owned atomic ordering point:

```text
persist/dedupe Telegram ingress input I
advance accepted_generation from G to G+1
associate I with the protected conversation/session authority state
```

Only after this durable state exists may the host acknowledge the input as accepted for responsibility purposes.

Failure after the commit but before pi-sand classification leaves:

```text
accepted_generation > admitted_generation
```

and therefore protected publication/final remain closed after recovery.

Duplicate Telegram delivery reuses the same stable input identity and does not advance responsibility twice.

## 6. Admission

After durable ingress, pi-sand classifies `input_id`.

### Ordinary status/question

```text
accepted_generation = G+1
classification = ordinary_question_or_status
revision unchanged
admitted_generation = G+1
```

No fresh Codex turn is required merely because a status message arrived.

### Correction

```text
accepted_generation = G+1
classification = correction
current_revision R -> R+1
old turn permanently retired from protected authority
fresh-turn transition performed
admitted_generation = G+1 only after the new canonical turn is safe/current
```

No protected publication/final authority is granted between revision change and successful fresh-turn admission.

## 7. Fresh-turn authority transition

Same-turn `turn/steer` is never sufficient authority proof after a revision change.

A material correction uses this sequence:

```text
1. durable input already advanced accepted_generation
2. commit InputDecision and new revision R+1
3. retire canonical T1 permanently from protected authority
4. request interruption/retirement of T1
5. wait for the host's reliable T1 terminal/retirement condition
6. prove the pinned process-containment boundary has retired all T1 Codex descendants that can write the authoritative workspace
7. drain/settle every other allowed T1 writer capability, including publication/recovery state that could later mutate local Git/workspace state
8. establish a fresh native turn on the same Codex thread
9. observe canonical lifecycle turn identity T2
10. bind T2 to Obligation O / revision R+1 under the same verified containment profile
11. set admitted_generation = accepted_generation
12. only now may protected effect/final authority reopen
```

Authority never binds from:

```text
process id
thread id alone
OpenClaw run label alone
model-authored revision
provisional turn submission id
same-turn steer acknowledgement
```

Once T1 is retired, any later T1 tool/final/protocol event remains stale regardless of when it arrives.

## 8. Protected writer surface is closed-world

v0.5 does not attempt to make arbitrary host callbacks safely cancellable or every filesystem mutation generation-aware.

Protected mode starts only if every authoritative workspace writer belongs to the pinned verified allowlist **and** the selected Codex execution profile provides descendant process containment strong enough to make teardown meaningful.

### Writer class A: contained Codex-native execution

Codex-native file/shell/background-terminal work may mutate the workspace **only under a pinned process-containment profile** whose teardown mechanically proves that no descendant process retaining workspace write capability can survive T1 retirement.

The contract is stronger than "Codex knows about its background terminals." The release proof must cover shell descendants that attempt to detach, create another process group/session, or otherwise outlive the initiating turn.

A Linux PID-namespace/process-lifetime sandbox may satisfy this requirement if the pinned OpenClaw/Codex combination proves descendant containment and teardown. The exact mechanism is host/runtime-owned; pi-sand does not implement a sandbox.

Uncontained profiles such as `danger-full-access` are incompatible with protected v0.5 unless the implementation independently proves an equivalent no-surviving-descendant writer guarantee.

Before T2 can gain authority over the same workspace, the host must prove both:

```text
all T1 Codex descendants capable of workspace writes are gone/isolated
Codex-owned background-terminal inventory/cleanup is settled
```

### Writer class B: Gateway GitHub publication

The `github_publish` tool exposed to Codex requests a Gateway-owned publication operation. It is not a general direct workspace callback capability.

Any publication-side local mutation that could affect the authoritative working state must either:

```text
be generation/current-authority checked immediately at its mutation boundary
OR
occur in an isolated/captured publication workspace that cannot corrupt the current authoritative workspace
```

A pending publication/recovery record that can later complete a local ref/index/worktree mutation is itself an outstanding writer capability. It must be fenced, completed under current authority, or isolated before T2 authority opens; an idle publisher process is not sufficient evidence of quiescence.

Remote push and PR creation are also protected mutations and require fresh authority at their own irrevocable boundaries.

### Forbidden writer classes/profiles

Protected mode must reject configuration that exposes:

```text
Codex execution without the pinned descendant-containment guarantee
unknown or third-party dynamic tools that can directly write the authoritative workspace
write-capable app/plugin/MCP paths not covered by the pinned contract
arbitrary callback handlers whose late mutation cannot be drained or isolated
```

Unknown/uncontained writer capability is not handled by pi-sand supervision; it makes the protected host profile incompatible.

## 9. Protected GitHub capability

The Codex execution placement must have no independent GitHub write credential/path.

Required negative capability checks include:

```text
GH_TOKEN absent
GITHUB_TOKEN absent
no authenticated gh profile mounted
no usable Git credential helper for GitHub
no private SSH credential / agent usable for GitHub
no write-capable GitHub MCP/App/connector
no operator keyring/credential store reachable by Codex
```

The only allowed write path is:

```text
Codex
-> github_publish
-> OpenClaw Gateway
-> required authority check/claim
-> credential-bearing publisher
-> GitHub
```

## 10. Logical effect identity and reconciliation

`effect_key` remains a host/Gateway publication identity, not a new pi-sand aggregate or table.

A logical identity may be derived from the current responsibility context, for example:

```text
(obligation_id, revision, "github-publication", candidate_fingerprint)
```

Its only purpose is to let the Gateway determine that restart/recovery is continuing the same logical publication operation rather than blindly creating a new one.

OpenClaw owns durable publication request state, Git transport, remote branch/PR readback, retry/reconciliation, and credential handling.

If GitHub accepted a mutation and the response was lost, recovery observes existing remote/publication facts before deciding whether another mutation is needed. No blind replay.

## 11. Publication/correction ordering

Every irreversible publication step has a one-shot host authority claim bound to current session generation + canonical turn + current revision + logical effect.

This includes publication-side local Git mutations that can alter the authoritative repository state, not only network push/PR calls.

Conceptually:

```text
C: correction/input durable acceptance
   -> accepted_generation G -> G+1

T: publication mutation claim
   -> assert accepted_generation == admitted_generation == G
   -> assert canonical turn/current revision binding
   -> persist/redeem one-shot claim for mutation step S
```

If C wins first, T fails.

If T wins first, mutation S may occur. A later correction cannot revoke a mutation already linearized; history/reporting must attribute S to the older responsibility state.

A later mutation in the same publication, such as local ref/index installation, push, or PR creation, requires its own current authority if it has not already been isolated from the current authoritative workspace.

## 12. Thin completion semantics

Codex final text is a completion candidate.

pi-sand authorizes completion only if responsibility facts permit it:

```text
candidate belongs to current canonical turn/current revision
accepted_generation == admitted_generation
explicitly required protected publication is resolved
explicit user-required blocking fact is satisfied
```

Example:

```text
"CI 过了以后告诉我"
```

requires an actual current-candidate CI success fact from existing GitHub/OpenClaw facilities before completion authorization.

v0.5 does not add a generic Reviewer, Evidence Framework, Completion Contract DSL, Result aggregate, or delivery subsystem.

## 13. Authoritative final dispatch

Semantic completion authorization is not enough by itself.

Immediately before the host commits the authoritative Telegram final delivery, OpenClaw must take a one-shot dispatch claim under the same current session authority ordering.

If a newer durable Telegram input wins first, the old final is withheld.

Protected profile must not expose an alternate model-controlled user-visible messaging path that bypasses this terminal dispatch gate.

## 14. Restart/fail-closed behavior

Protected conversation state survives host restart.

Required behavior:

```text
required authority owner absent/incompatible
-> protected session does not resume authoritatively

pinned process-containment profile absent/incompatible
-> protected session does not admit authoritative workspace execution

accepted_generation > admitted_generation
-> protected publication/final remain closed

retired turn event arrives late
-> remains stale

current canonical binding or writer quiescence cannot be proven
-> no protected authority until re-established
```

Never silently downgrade to ordinary OpenClaw hooks/Codex mode.

## 15. Pinned host/runtime contract

v0.5 supports one verified OpenClaw + Codex + execution-containment combination at a time.

Prototype #65 tested:

```text
OpenClaw ff63da7237e5f99e9fc03a86daf56e3c3e8f5356
Codex    a0dcfe2ada3f5bbd5059a34c0fc6fac244741a67
@openai/codex / codex-cli 0.151.0
```

A later independent review rechecked newer OpenClaw/Codex sources and found that the remaining writer-class issue is not the stale routing fence but process containment: background-terminal inventory alone is not enough to define all possible shell descendants.

Implementation may revalidate/pin a newer combination before release, but it must prove the same required authority **and descendant-containment** contract.

Version/capability/profile mismatch fails closed.

## 16. Required bounded OpenClaw host capabilities

v0.5 depends on a bounded host facility rather than today's ordinary fail-open hooks.

Required capabilities:

### H1. Required session authority + durable Telegram ingress generation

A protected session persists the required owner/contract and advances `accepted_generation` as part of durable protected ingress acceptance.

### H2. Canonical current-turn binding + pinned contained writer contract

The host can persist/observe which canonical native turn is current for protected authority, permanently retire old turns, and prove quiescence/isolation for the closed verified writer surface before a replacement turn gains authority.

For Codex-native shell/file execution specifically, H2 includes a pinned process-containment profile whose teardown proves that no T1 descendant retaining authoritative-workspace write capability can survive into T2 authority.

This is not a generic dynamic-tool sandbox or pi-sand process supervisor. Unknown/uncontained workspace writers are rejected from the protected profile.

### H3. Protected GitHub mutation authorization

The Gateway publisher asks the required authority owner / current session authority at each actual protected mutation boundary, including publication-side local Git mutation that can affect the authoritative repository, and binds the claim to current generation/turn/revision/effect identity.

### H4. Authoritative final-dispatch authorization

The host checks/redeems current authority at the real terminal user-visible delivery boundary. Missing/error/timeout withholds the final for protected sessions.

## 17. Required acceptance traces

Release evidence must include the dangerous interleavings, not only happy-path state.

### V05-01 — durable correction before classification

```text
Telegram correction durable
-> crash before pi-sand classification
-> restart
-> stale T1 attempts protected publication/final
```

Expected: both blocked because `accepted_generation > admitted_generation`.

### V05-02 — status query race

```text
status query durable
-> revision unchanged
-> old/current turn attempts publication while classification pending
```

Expected: blocked until admission; then same revision may reopen.

### V05-03 — late retired-turn traffic

After rev2/T2, inject/deliver late T1 dynamic-tool/final/protocol traffic.

Expected: it never enters the current protected route or gains authority.

### V05-04 — descendant process containment + background cleanup

T1 launches Codex-native workspace activity that attempts to outlive the turn, including:

```text
Codex-owned background terminal
child/grandchild process
attempted detached/new-session or new-process-group descendant where supported by the platform
```

Expected: under the pinned protected execution profile, T1 teardown proves no descendant retaining authoritative-workspace write capability survives before T2 protected admission. A late marker write after T2 authority opens is a release blocker.

### V05-05 — unknown/uncontained workspace writer

Attempt either:

```text
an unverified direct workspace-mutating dynamic tool
OR
a Codex execution profile without the pinned descendant-containment guarantee
```

Expected: protected profile refuses startup/admission or otherwise keeps protected authority closed. It must not rely on cooperative AbortSignal handling or terminal inventory alone.

### V05-06 — GitHub credential bypass

From Codex execution placement attempt all expected alternative GitHub write paths.

Expected: no usable write credential/path exists except Gateway publication.

### V05-07 — correction vs GitHub/local publication mutation

Race durable correction acceptance against a publisher mutation claim, including at least one publication-side local Git state mutation and the remote push boundary.

Expected: one ordering wins; no stale claim or pending recovery writer can mutate the current authoritative repository after a newer generation has won unless the operation was isolated from it.

### V05-08 — lost publication response

Remote mutation succeeds; response is lost; process restarts; user may send a correction before reconciliation.

Expected: observe/reconcile the old effect; do not blindly replay; any new mutation requires current authority. Pending recovery state that could mutate local Git remains fenced/isolated as a writer capability.

### V05-09 — correction vs authoritative final

Race durable new input against the actual terminal dispatch claim.

Expected: whichever claim/ingress commit wins defines order; no old final is delivered after a newer durable input won the fence.

### V05-10 — required authority/containment contract missing

Restart protected session without the required pi-sand owner/contract or without the pinned verified execution-containment profile.

Expected: fail closed; no silent ordinary-Codex or uncontained-execution downgrade.

## 18. End-to-end release journey

The release is complete when this works through Telegram 1:1:

```text
User: fix #123; tell me after CI passes
-> Obligation rev1 accepted
-> Codex T1 works under the pinned contained execution profile

User: do not change DB schema
-> generation fence closes immediately at durable ingress
-> revision becomes rev2
-> T1 retired
-> all T1 descendant/workspace writers and stale publisher recovery writers are proven quiesced/isolated
-> fresh canonical T2 on same thread under the same verified containment profile
-> T2 is the only protected current turn

User: reconnect too
-> correction/admission according to meaning
-> current responsibility represented by current turn

T2 produces candidate
-> CI fact observed
-> protected GitHub local/remote publication mutations occur only under current authority or isolation
-> final candidate passes thin responsibility gate
-> final dispatch takes current one-shot authority

System: completed
```

At every correction/crash boundary, stale execution may leave historical telemetry/work product but cannot newly perform protected GitHub mutation, corrupt the newly authoritative workspace through an uncontained writer path, or deliver authoritative completion.

## 19. Explicit implementation prohibitions

Do not implement v0.5 by adding any of these to pi-sand:

```text
AgentHarness wrapper/replacement
Codex protocol reimplementation
Codex process/thread supervisor
standalone pi-sand daemon as a new required boundary
scheduler / worker pool / DAG
generic process-containment/sandbox runtime
generic filesystem capability layer
generic dynamic-tool execution framework
generic Effect / Evidence / Result frameworks
second transcript store
GitHub credential/transport/reconciliation engine
Universal Host Interface
```

If a required invariant cannot be met without one of those, stop and revisit the architecture instead of rescuing it with more pi-sand runtime code.

## 20. Release exit criterion

v0.5 is successful when the following statement is mechanically true under the pinned contract:

> **One Telegram chat can hold one durable responsibility while Codex works in the background; a new durable user input fences protected action immediately, responsibility-changing corrections retire stale authority, only a canonical current turn running inside a verified descendant-containing execution profile can regain authority, GitHub local/remote publication writes cannot bypass the host capability boundary, and the system cannot authoritatively say “done” after a newer accepted user message has made that answer stale.**
